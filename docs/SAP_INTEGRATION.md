# SAP ECC integration runtime guide

MINA uses the licensed SAP Java Connector (JCo) supplied by the
customer. The connector is not redistributed with Studio. This implementation
interoperates with SAP ECC through public RFC/JCo contracts. MINA is an independent
product and does not include third-party proprietary connector implementations.

MINA itself is **not SAP-certified** merely because it uses JCo.
SAP permits JCo to connect external applications to SAP in both directions, but
the customer must download it from SAP, comply with named-user/solution licensing,
and must not redistribute the connector. Record the JCo, Java, OS, and CPU
architecture reported by Test Connection as part of every production approval.

## Supported integration patterns

| Pattern | Runtime behavior |
| --- | --- |
| IDoc Listener | Persistent registered JCo server, tRFC TID duplicate protection, bounded delivery queue, one workflow per IDoc in a package, enclosing transaction commit only after every IDoc succeeds |
| RFC/BAPI Listener | Persistent registered JCo server for the selected function, request/reply export and table response mapping, rollback when the task fails or omits Reply |
| Invoke RFC/BAPI | Persistent, bounded JVM worker pool; JCo destination pooling; import, changing, nested structure, and table parameters; request/reply, tRFC, and qRFC transport |
| Post IDoc / IDoc Reader posting | XML or rendered input is converted to EDI_DC40 and EDI_DD40 and sent with `IDOC_INBOUND_ASYNCHRONOUS`; tRFC or qRFC is selected at transport level |
| IDoc Parser / Converter / Renderer | Metadata-driven, byte-position fixed-width conversion with physical E2 to logical E1 normalization, configurable code page, strict/replace invalid-byte policy, and delimiter-safe flat records |
| Read Table | `RFC_READ_TABLE` field, filter, paging, and named-record output |
| Dynamic Connection | A dedicated persistent JVM and thread-bound JCo context across activities; explicit commit/end, rollback on failure/expiry, bounded session count, and duplicate-session rejection |
| IDoc acknowledgment / confirmation | Invokes the customer-configured SAP acknowledgment RFC because this function is solution-specific |

ALE distribution is implemented through the IDoc listener/posting paths. SAP
partner profiles, ports, process codes, message types, RFC destinations, and
authorizations remain SAP Basis configuration and are not generated by Studio.

## Required runtime files

Install a matching x64 JCo distribution in one of these locations:

```text
C:\ProgramData\MINA Studio\drivers\sap\sapjco3.jar
C:\ProgramData\MINA Studio\drivers\sap\sapjco3.dll
```

On Linux use `libsapjco3.so` next to `sapjco3.jar`, or select an explicit SAP
driver directory in the shared connection. The packaged Java runtime and JCo
native library must have the same architecture. Do not mix files from different
JCo releases.

Use a currently supported SAP JCo 3.1 patch and a JDK/JRE listed for that patch
in SAP Note 2786882. As of September 2026 SAP publishes JCo 3.1.14 and lists
Java 8, 11, 17, 21, and 25; re-check SAP's support page when qualifying a build.

## ECC configuration checklist

1. Create the RFC user with only the required S_RFC and IDoc authorizations.
2. Configure SM59 for the Studio Program ID, gateway host, and gateway service.
3. Configure WE21, WE20, message types, process codes, and partner profiles for
   ALE/IDoc traffic.
4. For qRFC, configure and monitor the queue in SMQ1/SMQ2 and set a non-empty
   SAP queue name in the activity.
5. Make each concurrently deployed registered server identity unambiguous.
6. Keep the TID store on durable writable storage. Never share one TID file
   between unrelated Program IDs.
7. Validate `STFC_CONNECTION`, fetch the actual IDoc/RFC metadata, and save the
   selected metadata with the project before packaging.

## Resource and failure behavior

- Listener event queues and stderr history are bounded. Backpressure reaches
  the JCo callback instead of permitting unbounded Python heap growth.
- Cancellation does not leave blocked Python executor threads. Runtime shutdown
  closes native listener processes and removes their temporary descriptors.
- The JCo server waits for the workflow result. Success commits the delivery;
  task failure, cancellation, missing RFC Reply, or reply timeout rolls it back
  so SAP can retry according to its transaction policy.
- TID state is persisted atomically. A previously committed or in-flight TID is
  rejected as a duplicate; SAP confirmation removes it.
- Single-call BAPI auto-commit executes `BAPI_TRANSACTION_COMMIT` in the same
  JCo context as the BAPI call.
- A Dynamic Connection with `transactional=true` pins all calls carrying its
  `sessionID` to one worker/JCo context. `contextEnd=true` closes the context;
  with `autoCommit=true` it first executes `BAPI_TRANSACTION_COMMIT`. Failure,
  expiry, or normal termination without `commitOnTerminate=true` rolls back.
- External outbound calls use persistent JVM workers. `outboundWorkerCount`
  controls Python-side worker concurrency; `poolCapacity`, `peakLimit`, and
  `connectionExpirationMilliseconds` configure the JCo destination pool in
  each worker. Changing any connection setting, including credentials, creates
  a distinct pool identity without storing plaintext credentials in its key.

## Flat IDoc and messaging modes

In JSON mode, the IDoc Parser and Converter expose one schema-shaped document
under `SAPIDoc`, for example `SAPIDoc.ARTMAS05.IDOC`. Map `SAPIDoc` to a Kafka
JSON payload to send that document once. Older direct runtime mapping paths
such as `SAPIDoc.IDOC` and `ARTMAS05.IDOC` remain available as lookup aliases;
they are not additional serialized JSON branches. Actual repeating IDocs and
segments remain in the payload.

The built-in parser reads canonical EDI_DD40 byte fields (`SEGNAM`, `MANDT`,
`DOCNUM`, `SEGNUM`, `PSGNUM`, `HLEVEL`, and `SDATA`) and EDI_DC40 control fields.
Set `idocEncoding` to the actual sender code page. Keep
`invalidCharacterPolicy=strict` for production unless replacement characters
are an accepted business rule. When SDATA may contain CR/LF, configure a unique
`idocRecordDelimiter`; that delimiter is authoritative and embedded line breaks
remain data. With no delimiter, canonical 1063-byte records are split by width.

If the separately licensed `sapidoc3.jar` is installed, Test Connection reports
its presence and version. Selecting the SAP JIDocLib parser engine validates
IDoc XML with SAP's repository-backed `IDocXMLProcessor`; flat EDI_DD40 input
continues to use the built-in byte parser because SAP documents the public IDoc
class-library processor as an XML processor.

IDoc Listener supports these sources:

- `NoMessaging`: the direct persistent JCo RFC server, including durable TID
  handling and SAP transaction acknowledgment.
- `EMS` or `JMS`: consumes one queue message through the selected shared
  connection and publishes its body to the parser. Client acknowledgment is
  exposed through the standard Confirm Message activity.
- `Kafka`: consumes one topic record through the selected Kafka resource and
  publishes its value to the parser. Manual offset confirmation uses the same
  Confirm Message contract.

For broker-backed modes, select `messagingResourceId` and
`messagingDestination`. SAP-to-broker transaction atomicity is owned by the
upstream bridge; MINA does not claim an XA transaction spanning
SAP tRFC and an independent EMS/JMS/Kafka broker.

## Production certification

Unit and mock tests verify serialization, lifecycle, transaction routing, and
bounded queues, but they cannot certify a particular ECC/JCo combination. Before
production, run an environment test with the exact JCo version and architecture:

- sustained IDoc batches containing the largest expected SDATA payloads;
- concurrent RFC/BAPI calls at the configured maximum connection count;
- SAP and Studio restart during in-flight tRFC/qRFC deliveries;
- duplicate TID, reply timeout, malformed IDoc, network partition, and expired
  credential scenarios;
- a 24-72 hour soak while recording process RSS, JVM heap/GC, thread count,
  handle count, queue depth, throughput, and SAP SM58/SMQ1/SMQ2 state.

Do not accept the connector for production until those measurements remain
stable and every failed transaction is demonstrably recoverable.

The repository includes a repeatable qualification runner and an intentionally
non-secret example configuration:

```powershell
Copy-Item docs\sap-soak-config.example.json sap-soak-config.local.json
# Edit the local copy with QA-only credentials and parameters, then run:
backend\.venv\Scripts\python.exe scripts\sap-production-soak.py `
  --config sap-soak-config.local.json --output sap-soak-report.json
```

Set `terminateWorkerEveryCalls` to a positive number for controlled worker-JVM
failure injection. Run separate 24–72 hour profiles for sRFC, transactional
BAPI and tRFC/qRFC IDoc posting. To qualify the 10-minute outbound target, set
`durationSeconds` to `600` and add `--target-calls 100000`. The report fails if
the 100,000th successful call falls after the deadline or a call fails. The report holds
throughput, failures, latency percentiles, and worker process IDs; correlate
those IDs with OS/JVM monitoring and SAP SM58/SMQ1/SMQ2 evidence. Never commit
the local configuration because it contains credentials.

### Qualifying SAP IDoc Listener throughput

The listener splits SAP packages by document number. Each callback waits for
all document workflows in the package. MINA reports a failed callback if a
document fails or if queue admission and workflow acknowledgements exceed the
configured `ackTimeoutSeconds`. SAP may replay the package, so use the
document number and business context for idempotency at downstream systems.
The bridge records its first inbound IDoc package and every thousandth
package thereafter, plus callback errors and startup diagnostics.

Use **Execution analytics → SAP IDoc deliveries** to compare document numbers
and SAP transaction IDs against the sender's list. In Run, the section shows
the outcome of each recorded delivery within the latest 100 workflow runs.
In Debug, it shows receipts in the current Debug log. **Activity invocations**
counts activity calls, including downstream steps. The HTML and JSON execution
reports include the delivery list. For older deliveries, use
the project runtime logs and search for `sap-idoc`. Bridge callback errors
are shown even when SAP sends no later document. An unsplit or malformed
batch is rejected so SAP can retry it.

The 10-minute target requires at least 166.7 completed documents per second.
On approved QA, send 100,000 unique IDocs with representative sizes from SAP
and verify downstream completions and SAP transaction confirmations within 600
seconds. Include the real downstream activities. Compare SAP packaging, RFC
registration count (`maximumConnections`), MINA workflow concurrency
(`maxConcurrentIdocs`, defaulting to the connection count), gateway limits,
disk latency, and the slowest downstream activity. Use one active listener per
registered Program ID on a host. Benchmark RFC/BAPI operations separately in
calls per second and distinguish them from IDocs per second. At eight workers,
sustaining the IDoc target requires a mean worker time below 48 ms even before
accounting for idle time.

The replay test exercises Listener → Parser → End with synthetic bridge
events and checks unique document numbers, segment values, and acknowledgements.
With backend dependencies installed, set `MINA_SAP_REPLAY_RECORDS=100000` and
run `python -m unittest discover -s backend/tests -p test_sap_idoc_throughput.py`
with `backend` on `PYTHONPATH`. It covers Studio Run and both Python exports.
The Java bridge test takes the document count as an argument and checks package
splitting, transaction duplicates, rollback, and restart behavior. Live SAP
gateway, native library, network, and downstream timings require the QA run.

The Windows development workspace recorded these synthetic results on
November 19, 2026. Each test checked 100,000 documents.

| Test path | Elapsed |
| --- | ---: |
| Java package splitting and TID storage | 74.19 s |
| Studio Run with rotating project logs | 342.91 s |
| Python engine archive | 88.97 s |
| Direct Python archive | 50.77 s |

Keep the TID properties file and its sibling `.committed` directory together.
The bridge reads committed entries from older properties files and writes a
marker for each new committed, unconfirmed TID. SAP confirmation removes the
marker. Preserve both paths during upgrades and wait for outstanding
transactions to confirm before reverting to a bridge that predates the markers.
