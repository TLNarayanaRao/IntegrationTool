# SAP ECC integration runtime guide

Integration Fabric uses the licensed SAP Java Connector (JCo) supplied by the
customer. The connector is not redistributed with Studio. This implementation
interoperates with SAP ECC through public RFC/JCo contracts; it is not SAP or
TIBCO software and does not include either vendor's proprietary implementation.

Integration Fabric itself is **not SAP-certified** merely because it uses JCo.
SAP permits JCo to connect external applications to SAP in both directions, but
the customer must download it from SAP, comply with named-user/solution licensing,
and must not redistribute the connector. Record the JCo, Java, OS, and CPU
architecture reported by Test Connection as part of every production approval.

## Supported integration patterns

| Pattern | Runtime behavior |
| --- | --- |
| IDoc Listener | Persistent registered JCo server, tRFC TID duplicate protection, bounded delivery queue, one workflow per IDoc in a package, enclosing transaction commit only after every IDoc succeeds |
| RFC/BAPI Listener | Persistent registered JCo server for the selected function, request/reply export and table response mapping, rollback when the task fails or omits Reply |
| Invoke RFC/BAPI | Import, changing, nested structure, and table parameters; request/reply, tRFC, and qRFC transport |
| Post IDoc / IDoc Reader posting | XML or rendered input is converted to EDI_DC40 and EDI_DD40 and sent with `IDOC_INBOUND_ASYNCHRONOUS`; tRFC or qRFC is selected at transport level |
| IDoc Parser / Converter / Renderer | Metadata-driven fixed-width segment conversion with physical E2 to logical E1 segment normalization |
| Read Table | `RFC_READ_TABLE` field, filter, paging, and named-record output |
| Dynamic Connection | Runtime connection overrides and bounded, expiring session identifiers |
| IDoc acknowledgment / confirmation | Invokes the customer-configured SAP acknowledgment RFC because this function is solution-specific |

ALE distribution is implemented through the IDoc listener/posting paths. SAP
partner profiles, ports, process codes, message types, RFC destinations, and
authorizations remain SAP Basis configuration and are not generated by Studio.

## Required runtime files

Install a matching x64 JCo distribution in one of these locations:

```text
C:\ProgramData\Integration Fabric Studio\drivers\sap\sapjco3.jar
C:\ProgramData\Integration Fabric Studio\drivers\sap\sapjco3.dll
```

On Linux use `libsapjco3.so` next to `sapjco3.jar`, or select an explicit SAP
driver directory in the shared connection. The packaged Java runtime and JCo
native library must have the same architecture. Do not mix files from different
JCo releases.

Use a currently supported SAP JCo 3.1 patch and a JDK/JRE listed for that patch
in SAP Note 2786882. As of September 2026 SAP publishes JCo 3.1.14 and lists
Java 8, 11, 17, 21, and 25; re-check SAP's support page when qualifying a build.

## ECC configuration checklist

1. Create the RFC user with only the required S_RFC and IDoc authorizations.
2. Configure SM59 for the Studio Program ID, gateway host, and gateway service.
3. Configure WE21, WE20, message types, process codes, and partner profiles for
   ALE/IDoc traffic.
4. For qRFC, configure and monitor the queue in SMQ1/SMQ2 and set a non-empty
   SAP queue name in the activity.
5. Make each concurrently deployed registered server identity unambiguous.
6. Keep the TID store on durable writable storage. Never share one TID file
   between unrelated Program IDs.
7. Validate `STFC_CONNECTION`, fetch the actual IDoc/RFC metadata, and save the
   selected metadata with the project before packaging.

## Resource and failure behavior

- Listener event queues and stderr history are bounded. Backpressure reaches
  the JCo callback instead of permitting unbounded Python heap growth.
- Cancellation does not leave blocked Python executor threads. Runtime shutdown
  closes native listener processes and removes their temporary descriptors.
- The JCo server waits for the workflow result. Success commits the delivery;
  task failure, cancellation, missing RFC Reply, or reply timeout rolls it back
  so SAP can retry according to its transaction policy.
- TID state is persisted atomically. A previously committed or in-flight TID is
  rejected as a duplicate; SAP confirmation removes it.
- Single-call BAPI auto-commit executes `BAPI_TRANSACTION_COMMIT` in the same
  JCo context as the BAPI call.

## Production certification

Unit and mock tests verify serialization, lifecycle, transaction routing, and
bounded queues, but they cannot certify a particular ECC/JCo combination. Before
production, run an environment test with the exact JCo version and architecture:

- sustained IDoc batches containing the largest expected SDATA payloads;
- concurrent RFC/BAPI calls at the configured maximum connection count;
- SAP and Studio restart during in-flight tRFC/qRFC deliveries;
- duplicate TID, reply timeout, malformed IDoc, network partition, and expired
  credential scenarios;
- a 24-72 hour soak while recording process RSS, JVM heap/GC, thread count,
  handle count, queue depth, throughput, and SAP SM58/SMQ1/SMQ2 state.

Do not accept the connector for production until those measurements remain
stable and every failed transaction is demonstrably recoverable.
