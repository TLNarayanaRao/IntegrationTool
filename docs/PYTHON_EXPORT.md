# Python archive modes

Studio exposes two distinct Python exports. Both contain Python application files and `manifest.json` for Control Plane package metadata; neither includes project, task, or resource JSON descriptors.

- **Export direct Python / Deploy direct Python** compiles supported task transitions into async Python state machines. The generated task source contains direct `if`/`elif` flow decisions, inline group conditions/loops, `asyncio.gather` for success fan-out, and typed Python references for property and activity bindings. It does not bundle the MINA workflow engine. The exporter rejects unsupported semantics with activity names instead of silently substituting an engine-backed implementation. Supported paths include Start, End, Scheduler, Log, Mapper (including functions, conditions, and repeating targets), Call Sub Task, global and transition Catch, Throw, Rethrow, General activities (Empty, Assign, Sleep, Checkpoint, shared variables, and External Command), File, FTP/SFTP, hosted and outbound HTTP/REST/SOAP, HTTP Response, XML/JSON/flat-data parse and render, Excel Read, Transform, Python/Java Invoke, JDBC, Snowflake, AMQP, Kafka, Pub/Sub, EMS/JMS send, receive, request/reply and reply, and supported SAP operations and IDoc parsing. Scheduler, Kafka, Pub/Sub, EMS, JMS, SAP, HTTP, REST, and SOAP starters remain active until stopped. SAP IDoc listeners support direct JCo and EMS/JMS/Kafka messaging sources. Single-entry/single-exit If, For Each, Iterate, While, Repeat, Repeat-on-Error, JDBC transaction, and critical-section groups compile to explicit Python control flow and may be nested with mixed group types. Client-acknowledge JMS receivers use a persistent bridge session and Confirm Message can acknowledge an active delivery.
- **Python compatibility archive (engine-backed)** retains the full Python runtime engine and the existing wider activity/group behavior. It remains deployable but is not a full direct-code conversion. The package manifest records `pythonSource.mode: engine` so consumers can tell which implementation they received.

The standard `.mpkg` and `.ear` exports remain available. Python archives require separately licensed vendor drivers where the underlying connection needs them (for example SAP JCo or JMS/EMS). A Python source package does not replace those vendor libraries. Legacy `.ifpkg` packages remain importable.

Engine-backed Python archives select connector modules from the packaged activities and groups instead of copying every engine file. All included Sub Tasks participate in selection, and JDBC transaction groups include the JDBC adapter. The exporter follows adapter imports transitively (including Java bridge dependencies and the JDBC adapter's Snowflake support). Shared scheduling, model, mapping/expression, and timestamp modules remain in every engine-backed archive. Optional connectors load only when executed; unused shared connection definitions do not cause their connector modules to be bundled. Standard JSON-based EAR archives do not contain this Python engine.

Direct archives are capability-linked from the persisted project model and selected task closure. The linker never checks project names, sample identifiers, known canvas layouts, or a catalog of previously exported applications. It records the exact activity operations and group types in `application/capabilities.py`, removes unreachable execution branches, specializes connector functions to the operations used by the project, and omits unreferenced activity modules, connector modules, native adapters, inbound servers, shared resources, schemas, and properties. Referenced shared resources are followed transitively, as are XSD `schemaLocation` and JSON Schema `$ref` dependencies, so dependency pruning does not produce an incomplete package. Its registry is required to cover every activity operation advertised by the direct exporter; adding a future supported Studio activity without linker metadata fails the exporter and its coverage test instead of silently generating an incomplete application. A property-driven resource, schema, or SAP messaging-provider selection conservatively retains compatible candidates because the selected object can change between packaged environments. Packaging never removes something required by a selected environment merely to make the archive smaller.

For a successfully compiled direct archive, run `python exported.pympkg --task TASK_ID --input '{"key":"value"}'` on a standard Python host. No extraction or source edit is needed. Alternatively, extract the archive and use `python run.py` as a Python-script job entry point (including a Databricks Python script task); pass `--environment PROFILE` when multiple profiles are packaged, and `--task TASK_ID` for a single task. Without `--task`, the generated application runs the selected starters; receiver starters keep polling until stopped. If no environment is specified, the first packaged profile is used.

Run `python run.py --check` (or `python exported.pympkg --check`) in the target data plane before deployment. The generated preflight checks only the dependencies used by that application, returns machine-readable JSON, and exits with code `2` when a required package, Java runtime, or external project artifact is missing. The Control Plane manifest also exposes the preflight command and dependency inventory.

For qualification against real providers, run `python run.py --qualify-task TASK_ID --input '{"test":true}' --iterations 1000 --concurrency 10`. Optional thresholds include `--max-error-rate`, `--max-p95-ms`, and `--max-memory-growth-mb`; `--duration-seconds` turns the same command into a bounded soak test. The command exercises the actual exported task and produces JSON evidence containing throughput, success/failure counts, latency percentiles, bounded error samples, and Python memory growth. It exits with code `3` when a threshold fails. Provider failover is tested by running this command while performing an approved broker/database/SAP failover in the test environment.

Real connectors require runtime provisioning, not source edits. Set `FABRIC_JAVA_BRIDGE_HOME` to the installed Java bridge directory containing `classes`, and `FABRIC_DRIVER_HOME` to a directory containing `sap/` and/or `jms/` licensed vendor JARs. Rebuild the bridge from this source before deploying client-acknowledge JMS flows. Place the SAP JCo native library in the SAP driver directory or on the platform native library path. A Java runtime must be available via `FABRIC_JAVA` or `PATH`. Depending on the generated preflight inventory, install `aiokafka`, `google-cloud-pubsub` and `google-auth`, `openpyxl`, `paramiko`, `snowflake-connector-python`, `pika`, or `azure-servicebus`. Provide connection URLs, credentials, and target-network access through the selected environment profile or environment variables. Missing packages and artifacts are reported before application startup.

The direct export is not a blanket compatibility promise for every future Studio feature. Grouped parallel fan-out still requires an explicit top-level branch boundary because a deterministic in-group join is not represented in the saved graph. Live ECC/JCo, EMS/JMS provider, AMQP, Snowflake, failover, and soak results cannot be asserted without those systems; use the generated qualification command in the target test environment and retain its evidence before approving production. The automated suite covers hosted REST, JMS request/reply correlation, SAP-over-Kafka, mixed nested groups, mock/in-memory providers, SQLite transactions, and bridge compilation. The saved `order-integration` project passes direct compiler static validation, which is not itself a live SAP qualification. Export reports unsupported graph behavior instead of generating a package with silently different behavior.
