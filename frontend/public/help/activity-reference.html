This guide documents the behavior implemented by Integration Fabric Studio and its local runtime. It is bundled with the installer, opens without internet access, and describes the product’s own contracts rather than redirecting to third-party manuals.

Design fundamentals

Configuration

Design-time defaults, resources, operation modes, and schemas.

Input

Drag source fields, functions, constants, or environment properties to simple target fields.

Output

The published schema becomes selectable data for downstream activities.

Complex elements are structural and are populated through child mappings. Repeating complex elements support For Each and For Each Group. Environment expressions use ${properties.key}; execution data uses the Data tree. Validate a task before Run or Debug.

Activity reference

Start, End and Call Sub Task

Start declares a callable task input boundary. Event-driven starter tasks normally begin with a receiver instead. End publishes the final result. Call Sub Task invokes a reusable Sub Task and returns its End output.

  • Use static Task selection when the dependency must be packaged automatically.
  • Use Dynamic Task Override for an environment-, input-, or output-derived target.
  • Map only simple fields and attributes; expand complex structures to map their children.
Typical flow
Start → Mapper → Call Sub Task → End

Scheduler

Starts a task at a date/time or cron schedule. Run and Debug deploy the schedule as a continuous listener; downstream execution starts automatically when the schedule fires.

  • Choose Date & Time or Cron.
  • Use the active environment’s timezone and properties.
  • Run once now is intended for local Run/Debug verification.
Runtime
Ready → schedule event → task execution → ready

Mapper

Builds schema-aware output using manual mappings, typed constants, functions, conditions, and repeating structures. The expanded editor and Map & Test surface execute the same saved rules as runtime.

  • Drag a repeating source complex element to a repeating target to create For Each automatically.
  • Use an explicit index such as [1] to select one occurrence.
  • Strings require quotes; numeric and boolean constants are type checked.
  • AI suggestions remain reviewable before they become active mappings.
Verify
Choose target schema → map → Map & Test → validate output

Transformer

Runs Integration Fabric’s DataWeave-compatible transformation subset for JSON, XML, and text mediation. It supports payload, attributes, variables, selectors, objects, arrays, defaults, conditionals, coercions, and common collection operations.

  • Use the editor test input before runtime.
  • Select the output MIME type and output target.
  • Unsupported syntax produces DATAWEAVE_SYNTAX, not a silent fallback.
Example
%dw 2.0
output application/json
---
{ id: payload.id }

XML, JSON and Parse Data

Parse activities turn serialized input into typed trees; render activities serialize mapped structures. Parse XML returns XML metadata and an XSD-shaped value tree. Parse JSON returns JSON. Parse Data accepts text or a file path and emits an XML record document.

  • Select or define a schema to publish exact mapping fields.
  • Configure duplicate-key, null, encoding, delimiter, header, and line-ending policies as appropriate.
  • Render XML maps attributes with @name and text with #text.
Patterns
Read File → Parse XML
Start → Parse JSON → Mapper
Parse Data → Render XML

File, FTP, SFTP and Excel

File activities read, write, list, copy, rename, delete, and poll. FTP and SFTP perform remote equivalents through shared connections. Excel reads one worksheet or every tab and creates nested JSON from dotted column headers.

  • All paths may be mapped or sourced from environment properties.
  • File Poll is a continuous event receiver with Created, Modified, Deleted, and Any modes.
  • SFTP host-key and private-key policy belongs in the shared connection.
Excel
Blank worksheet = all tabs
customer.address.city = nested fields

HTTP, REST and SOAP

Receiver activities publish a local endpoint and start the task for matching requests. Invoke activities make outbound calls. HTTP Response completes the active inbound exchange with mapped status, headers, and body.

  • Listener host, port, TLS, and authentication come from a shared HTTP connection.
  • Run/Debug displays the live endpoint in Execution & Debug.
  • REST paths, query values, headers, and SOAP payloads remain available as mapping trees.
Service flow
REST Receiver → Mapper → HTTP Response

JDBC, Databricks and Snowflake

The SQL designer supports query, update, procedure, and direct SQL patterns. Named parameters such as :customerId become typed Input fields. Shared connections control database driver, pool, authentication, TLS, catalog, and schema details.

  • Fetch metadata to browse tables and result columns.
  • Choose a datatype for every derived parameter.
  • Java JDBC mode uses JAR drivers; native Python modes use their packaged adapters.
  • Snowflake adds entity metadata and staged bulk-load settings.
Prepared query
SELECT * FROM orders
WHERE id = :orderId

EMS and provider-neutral JMS

Queue/topic receivers start tasks automatically and remain ready continuously. Send, publish, request/reply, browse/get, reply, and Confirm Message use the selected shared connection and destination policy.

  • Direct EMS requires URL, username, and password; connection ID is generated when absent.
  • JNDI fields become required only when JNDI mode is enabled.
  • Client acknowledgement output maps to Confirm Message acknowledgement handles.
  • Provider libraries belong in the documented driver directory before external testing.
Client acknowledge
Queue Receiver → process → Confirm Message

AMQP, Kafka and Google Cloud Pub/Sub

These event connectors publish and receive typed messages using shared, environment-driven connection settings. Receive/subscribe activities run continuously; manual acknowledgement handles can be confirmed downstream.

  • AMQP supports send, receive, get, and dead-letter behavior.
  • Kafka exposes topic, key, headers, partition, offset, and commit information.
  • Pub/Sub accepts a JSON service-account credential and exposes data, attributes, ordering key, and acknowledgement ID.
Event flow
Receiver → Mapper → business activities → Confirm

SAP ECC

SAP activities cover RFC/BAPI invocation and listener flows, IDoc parsing/rendering, posting, acknowledgement, confirmation, and table reads. Retrieved IDoc metadata is stored with the shared SAP connection and drives activity schemas.

  • Test the connection before retrieving metadata.
  • Select a release and IDoc type to publish the correct segment tree.
  • Use the TID manager for transactional duplicate protection where required.
IDoc flow
IDoc Listener → Parse IDoc → Mapper → business target

General activities and custom code

General activities include Assign, Sleep, Checkpoint, shared-variable access, and External Command. Java and Python activities invoke packaged or selected code artifacts and publish method/function results.

  • External Command uses an argument array and does not require a shell.
  • Configure working directory, environment, stdin, timeout, and output capture.
  • Package referenced code artifacts with the project.
Security
Avoid shell interpolation. Keep secrets in environment properties and deployment secret providers.

Errors, logging and retry

Catch, Throw, and Rethrow define fault paths. The Errors tab selects propagate, continue, or transition handling. Log writes structured application events. Advanced automatic payload logging and outbound retry are environment-property driven.

  • Project logs roll at the configured size and remain available from the runtime log viewer.
  • Retry settings appear only for activities that make outbound target-system calls.
  • Password properties are masked and excluded from ordinary package configuration output.
Recommended
Catch specific faults → Log context → compensate or Rethrow
